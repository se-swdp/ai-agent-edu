# 노트필기 공유 스타일 발표자료 제작 가이드

## 이 스타일의 정체

이 레포의 발표는 강의가 아니라 **먼저 겪어본 사람이 자기 필기 노트를 옆에서 펼쳐 보여주는
자리**다. 제목부터가 선언이 아니라 경험담이다 — "AI Agent와 **일해보니**",
"AI Driven 전환은 **왜 어려운가**", "**부려 보면, 안다**". 청중은 가르침을 받으러 온 게
아니라 남의 노트를 구경하러 왔고, 그래서 어깨에 힘이 빠진 어투와 손글씨 질감이 본질이다.
이 전제가 아래 모든 규칙의 이유다: 노트는 문장이 짧고, 화살표와 배너로 생각의 흐름을 남기고,
출처를 귀퉁이에 적고, 소결을 크게 눌러쓴다.

## 시작 전에 결정할 세 가지

1. **청중과 전제 수준.** 기존 5종이 이미 커버하는 조합(혼합 일반청중 / SWDP 조직 /
   전환 담당 / 전직군 범용 / 개발자 실전)과 겹치는지 `presentations/*/README.md`로 확인한다.
   40% 이상 겹치면 신작이 아니라 기존 덱의 개정이 맞는지부터 의심한다.
2. **척추 문장 하나.** 발표 전체를 관통하는 한 문장을 먼저 확정한다.
   예: "병목이 '구현'에서 '인지'로 이동했다"(ai-checkpoint), "AX는 도구 보급이 아니라
   업무 운영체계의 문제"(ai-driven-transition). 척추 문장은 훅에서 등장하고, 중반 소결에서
   변주되고, 클로징에서 회수된다. 이게 없으면 슬라이드 모음이지 발표가 아니다.
3. **형식.** 기본값은 손글씨 노트 이미지 덱(전역 note-deck 스킬 파이프라인).
   코드·커맨드·터미널 출력이 많으면 하이브리드(개념=이미지, 코드=HTML 슬라이드 —
   claude-code-playbook 방식)를 쓴다. 손글씨로 코드를 그리면 가독성이 무너지기 때문이다.

## 어투 규칙

- **개조식 중간 톤.** 완전한 존댓말도, 반말도 아닌 노트체 — "만들기는 쉽다 — 운영이 어렵다",
  "하나씩 살펴보기!". 존댓말 문장("살펴볼게요")은 노트가 아니라 대본처럼 읽히므로 피한다.
- **긴 문장 금지.** 슬라이드 위 문장은 노트 필기 길이. 부연은 발표자의 입(나레이션)이 담당하고,
  슬라이드는 기억의 앵커만 남긴다.
- **펀치라인은 대구(對句)로.** "읽기는 넓게 / 쓰기는 좁게 / 게이트는 사람",
  "맥락은 주고 — 경계는 긋고 — 판단은 사람이", "원칙은 채택, 실행은 SWDP에 맞게".
  줄표(—)와 가운뎃점(·)이 이 문법의 구두점이다.
- **은유는 발표당 한두 개를 깊게.** "IDE는 인간용 안경", "자동차보다 도로", "토큰 팩토리"처럼
  하나의 은유를 여러 장에 걸쳐 회수한다. 장마다 새 은유를 꺼내면 노트가 아니라 광고가 된다.
- **기술 용어는 원문 유지.** Harness, MCP, PR 같은 용어는 억지로 번역하지 않고
  괄호 병기나 원어 그대로 쓴다.

## 서사 설계

- **텐션 곡선을 먼저 그린다.** 검증된 패턴: 낙관 → 현실의 마찰 → 종합(ai-checkpoint),
  질문 → 10가지 구조 → 처방(ai-driven-transition), 기준선 → 개념 → 실천 → 사례 → 사람(working-with-agents).
  낙관만 있으면 벤더 발표, 비판만 있으면 냉소가 된다 — 양쪽 인용을 의도적으로 배치한다.
- **구간 전환에는 브릿지 슬라이드.** 구간의 마지막 장이 다음 구간의 문을 연다
  (예: "여기까지가 낙관의 곡선" 소결이 마찰 파트 진입 브릿지).
- **수미상관.** 커버·훅의 질문을 클로징에서 반드시 회수한다. Q&A 장에는 답이 아니라
  청중이 스스로에게 던질 유도 질문 2~3개를 남긴다("우리 팀의 병목은 아직 구현인가").

## 슬라이드 문법 (타입별)

| 타입 | 규칙 |
|---|---|
| 커버 | 제목 + 부제(척추 문장의 예고). 장식은 그림이 담당, 텍스트는 두 줄이면 충분 |
| 훅 | 2번 장. 질문 또는 충돌하는 숫자·인용으로 시작 ("단가는 반값인데 예산은 왜 4월에 끝났나") |
| 세 숫자 훅 | 큰 숫자 3개만 (88 / 5 / 95). 해석은 아래 한 줄, 출처는 귀퉁이 |
| 디바이더 | 원형 번호(①②③…) + 구간 제목 + 부제 한 줄. 부제에 컷된 소결 문구를 흡수할 수 있다 |
| 본편 | 한 장 = 한 주장. 통일 템플릿 권장: 현상 + 메커니즘 + 출처 + 처방 배너 (ai-driven-transition 8–17장 방식) |
| 소결 배너 | 구간이 끝날 때 큰 글씨 한 문장. 발표의 클라이맥스는 소결 배너에서 나온다 |
| 클로징 | 요지 + Q&A 유도 질문 + 출처 한 줄. 별도 출처 전용 장은 만들지 않는 게 기본 |

- 분량 기준: 40분 발표 = 본편 15~20장 + 오프닝·디바이더·소결·클로징 = 22~28장.
  57장(working-with-agents)은 부록 포함 상한선이었다 — 조직·심화 내용은 본편이 아니라
  **클로징 뒤 부록**으로 빼고 "시간 여유 있을 때만"으로 선언한다.
- HTML 기획 → 노트 덱 압축 시: 소결 배너·출처·Q&A 단독 장을 먼저 컷하고 핵심 문구는
  디바이더 부제와 클로징에 흡수한다 (28→22장 압축의 검증된 순서).

## 숫자와 인용의 규율

이 스타일의 신뢰는 손글씨의 느슨함과 숫자의 엄격함의 대비에서 나온다.

- **모든 통계는 제작 당일 1차 출처로 재검증**한다 (working-with-agents가 13종 발표 통합 시
  METR·Stanford AI Index·MIT NANDA를 전수 재검증한 전례). 귀속이 틀리면 정정한다
  (Clark→Amodei 귀속 정정 전례).
- 수치·인용에는 출처를 슬라이드 귀퉁이(.meta 또는 손글씨 각주)에 짧게 표기한다.
- **반대편 인용을 의무 배치.** 낙관 구간에 벤더·빌더 인용을 쓰면, 마찰 구간에
  비판자(Willison, Ronacher류) 인용을 같은 무게로 싣는다.
- 본문에서 컷된 인용의 출처가 클로징 출처 라인에 남아있지 않은지 확인한다
  (HBR 잔존 사례 — 정합성 감사에서 잡힌 실수).

## 제작 파이프라인과 검증

1. **기획서**: 척추 문장·텐션 곡선·구간표(슬라이드별 펀치라인 포함)를 먼저 쓰고 팩트체크를 돌린다.
2. **이미지 생성**: 전역 note-deck 스킬 사용 (1672×941, codex image_gen, 스타일 레퍼런스,
   webp q95 인코딩, 뷰어 패키징). 국소 수정은 원본 PNG를 `-i`로 첨부하는 Recipe 3
   ("Recreate EXACTLY … with ONLY these changes").
3. **정합성 감사**: 완성 후 4렌즈(숫자·비주얼·카피·서사) 병렬 감사를 돌린다. 손글씨 생성은
   오타가 섞인다 — "건너띔", "TH1.1→THI.1" 같은 글자 결함은 확대 검수로만 잡힌다.
   오탐도 있으니(정상 표기를 오타로 오인) 확정 결함만 Recipe 3으로 국소 재생성한다.
4. **README 기록**: 구성표(구간·페이지·내용), 압축·컷 내역, 재생성 이력을 덱 README에 남긴다.
   README가 이 레포의 제작 기억이다 — 다음 덱이 전례를 검색하는 곳.

## 레포 등록 절차

1. `presentations/<slug>/` 생성 — 뷰어는 `index.html`(폴더 URL 계약), 이미지는 `NN-slug.webp`,
   원본 PNG는 `src-png/`(gitignore됨).
2. `presentations/index.html`의 nav에 카드 한 줄 추가 — title/sub/date만 쓰면
   번호·집계·열람실 manifest는 전부 자동 파생된다 (손으로 세는 값 없음).
3. 배포: `firebase deploy --only hosting:agent --project swdp-seminar-dashboard`
   (predeploy 훅이 manifest 자동 생성). git push만으로는 사이트가 안 바뀐다.
